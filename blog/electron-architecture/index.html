Electron 架构：主进程权威态与多窗口管理

August 28, 2026

桌面版采用 Electron 封装 Web 前端，一次获得多屏投屏、本地文件、SQLite 持久化与自动更新能力。Electron 模块位于 electron/（main / window-manager / ipc-hub / db / storage-layout / tray / updater / preload）。

主进程权威态（Single Source of Truth）

系统有主控制窗与两个投屏窗（竞价页 / 欢迎页），它们是独立渲染进程。多窗口同时写入必然冲突，因此主进程持有 canonicalState / canonicalConfig 作为唯一权威态：

控制台 push-state
  → db.persist(state)                  # SQL 落盘
  → canonicalState = state             # 更新权威态
  → broadcastToDisplays('state-sync')  # 广播所有投屏窗

投屏窗只读不回写：挂载时 request-state 回拉最新态，随后订阅 state-sync 实时刷新。崩溃重启后可立即回拉，状态不丢。

配置即时通道

config 负载小且变化频繁（主题、字号）。若与整份 state 共用 300ms 防抖落盘通道，副屏需等待防抖才响应。config 单独走 push-config（50ms 防抖，仅内存广播不落盘），实现"即改即现"；整库持久化仍由防抖的 push-state 负责。

投屏窗崩溃自动恢复

监听 render-process-gone 后 600ms 自动重建投屏窗（最多 3 次），连续崩溃则回发 display-crashed 通知控制台。窗口管理器统一登记所有窗口，创建 / 销毁 / 恢复集中管理。

持久化：sql.js

选型 sql.js（纯 WASM SQLite）而非 better-sqlite3：免 native 重编译，asarUnpack 确保 WASM 文件打包后可访问。代价是需手动 flush() 落盘——主进程单写者模型满足该约束。表结构为 kv + targets + media / deal_artifacts，增量 upsert + prune 兜底清理孤儿行。

打包流程

electron-builder 打包链路包含两个自定义钩子：

  • prep-installer.cjs：打包前预解压 winCodeSign（跳过符号链接，规避 CI 环境问题）；
  • after-pack.cjs：打包后注入 pm 应用图标与版本信息（rcedit）。

三宿主兼容

bridge.js 统一抽象 Electron / WebView2 / 纯浏览器三种宿主，方法名一致（LoadState / OpenProjection / PickFile…），业务代码不感知运行环境——同一份前端，桌面端使用真投屏与 SQLite，浏览器端自动降级为 window.open 与 localStorage。
